# IMPORTANT TERMS-
1. users -> person using the app.
2. account -> financial identity associated with users.
3. wallet -> a container that shows available money to use. It is the view of money, not the source of truth.
4. Balance -> amount available for users to use.
Available Balance -> can be spent immediately 
Blocked Balance -> Reserved for a pending transaction
Total Balance -> Available + Blocked

5. Ledger -> immutable book of financial entries, instead of editing history we add a new record.
6. Ledger entry -> a single financial movement. It has 2 types (CREDIT, DEBIT).
7. Double-entry accounting -> Every transaction affects 2 accounts (sender and reciever)

8. Transaction -> A business operation representing a money movement.
{
  from: "rohit@payflow",
  to: "alice@payflow",
  amount: 500,
  status: "SUCCESS"
}
One transaction can have multiple ledger entries.
9. Transaction reference ID -> unique ID for identifying transaction.
10. Payment intent -> an object used to track payment process from start to finish. Useful for idempotency, retry handling, and payment confirmation flows.
common states -
a. Initialized: The payment object is created, but no money movement has started yet.
b. Processing: The system is waiting for the bank or network to reply.
c. Succeeded: The payment finished with no errors.
d. Failed/Canceled: The payment was blocked, declined, or stopped.

11. Transaction State -> the current state of processing.
INITIATED, VALIDATED, AUTHORIZED, PROCESSING, SUCCESS, FAILED, REVERSED.
12. Authorization -> permission to perform transaction. 
In UPI -
a. MPIN verification
b. device verification
c. biometric approval
13. Settlement -> final exchange of money between the financial entities.
a. in this project, wallet transaction can be treated as immedate settlement.
b. in real UPI apps, Banks settle balances through NPCI and RBI systems later.
14. Reversal -> undoing of a complete transaction. Reversal is creation of a new transaction NOT deleting the old one.

15. Atomicity -> all operation succeed or none.
16. idempotency -> dempotency means that you can do the same action many times, but the final result stays the same as doing it just once.
The first time server sees the key - 

Key doesn't exist
       ↓
Process payment
       ↓
Payment succeeds
       ↓
Store key + result

Idempotency doesn't mean:"Don't allow two payments at the same time."
It means: "Don't process the same payment request more than once."

17. Concurreny -> multiple operation happening at the same time.

18. UPI-ID/ VPA -> virtual payment address ex.rohit@payflow. Maps to an underlying account or wallet.
19. Payment Service provider -> the app that provides the payment interface. ex. PhonePe, GooglePay, PayTm.
20. Benificiary -> the person recieving the money.

21. Aggregation pipeline -> A sequence of operation that transform the data.
22. Running balance -> balance after each transaction. Useful for passbook style settlement.

23. Sessions -> Represent the loggedIn device. 
{
  userId,
  deviceId,
  refreshTokenHash,
  expiresAt
}
Allows, logout from one device, logout from all device, session tracking.

# TRANSACTION STATES - a payment isn't necessarily immediately successful or failed.
It has multiple states.
-INITIATED - The user has requested a payment. Money hasn't necessarily moved yet.

-PROCESSING - the system has accepted the request and is currently working on it.

-SUCCESS - everything completed correectly

-FAILED - something prevented the payment from completing. No money should have moved.

-REVERSED - sometimes we may need to reverse the money. We don't delete the original successful transaction. 
insted we create a new another financial operation.

-EXPIRED - Sometimes a payment request remains unresolved for too long. This prevents the transaction from remaining indefinately in "PROCESSING".
EXPIRED DOES NOT MEAN THAT money automatically comes back.
EXPIRED means the payment request was not completed within the allowed time. What happens to the money depends on whether money was merely reserved, actually transferred, or still uncertain.

# BALANCE RESERVATIONS/HOLD

ex- Suppose Rohit has: Wallet balance = ₹1,000
He starts a payment of: ₹700. But the external payment system may take 30 seconds to respond.
During those 30 seconds, what should PayFlow consider Rohit's balance to be?
This is where reservations (holds) come in.
"This ₹700 belongs to this payment attempt now. Rohit cannot use it for anything else until we know what happens."
RESERVED
   │
   ├── SUCCESS → CAPTURE → money moves
   │
   ├── FAILED  → RELEASE → money becomes available
   │
   └── EXPIRED → RELEASE
                    │
                    └── unless external system actually
                        moved the money
EXPIRED does not automatically mean money should be returned. It depends on what actually happened.

If the money was merely reserved:
EXPIRED
→ release reservation

If the money had already been debited:
EXPIRED
→ investigate external state
→ potentially reverse/refund

One wallet can have multiple reservations.
ex- Balance = ₹2,000, start three payments
PAY-A = ₹500
PAY-B = ₹700
PAY-C = ₹300

Reservations:
PAY-A → ₹500
PAY-B → ₹700
PAY-C → ₹300

Total reserved: 1500

therefore, Balance: ₹2,000 Reserved:  ₹1,500  Available: ₹500.He can only initiate another payment up to ₹500.

Available Balance = Total balance - reserved amount.

# TIMEOUT - Timeout means uncertain outcome

ex. Rohit has: Balance = ₹1,000
He sends: ₹700
PayFlow reserves it: Balance = ₹1,000, Reserved  = ₹700, Available = ₹300.
PayFlow sends the request externally: PAY123 → ₹700
Then: No response.
After 10 seconds: TIMEOUT.

At this moment, PayFlow should conceptually think:
PAY123
Status = UNKNOWN / PROCESSING, NOT status = FAILED

What happens next ? PayFlow needs to determine what actually happened. It uses different mechanism for that-
A. Query the external system
Ask: "What is the status of PAY123?", External responds: PAY123 → SUCCESS. Now payflow knows
B. Reconciliation
If the external system provides transaction records later:
PayFlow:
PAY123 → PROCESSING/TIMEOUT

External:
PAY123 → SUCCESS
₹700
Reconciliation detects the mismatch. Payflow can then resolve it.

So, timeout simple means - 
TIMEOUT
   ↓
Don't assume failure
   ↓
Keep money protected
   ↓
Find out what happened

Eventually we discover the truth.
A. External says SUCCESS 
PAY123 (External = SUCCESS)
Reservation
     ↓
CAPTURE
     ↓
DEBIT
     ↓
Ledger, Rohit ends up with 300

B. External says FAILED
PAY123 (External = FAILED)
Reservation
     ↓
RELEASE, Rohit gets his ₹700 back as available money. Final: 1000 available

C. Still can't determine
Suppose even reconciliation can't immediately determine the outcome.
Then PayFlow may keep the payment in an unresolved state:
PAY123 (Status = INVESTIGATING), and keeps the money protected according to the policy


# LIMITS AND RISK Engine - 
Even if sender has enough money, should PayFlow allow this transaction?

                    Payment request
                          │
             ┌────────────┼────────────┐
             ▼            ▼            ▼
        Can afford?   Within limits?  Safe?
             │            │            │
          Balance       Limits        Risk

- what are limits ? Limits are explicit business rules.
Per-transaction limit : Maximum = ₹20,000
So: ₹10,000 → allowed, ₹20,000 → allowed, ₹25,000 → rejected.

Daily limit: Daily limit = ₹50,000
already sent: ₹15,000, ₹10,000, ₹20,000, total: 45,000
Now he tries sending -> 10,000. Balance might be sufficient, but ₹45,000 + ₹10,000 = ₹55,000, which exceeds daily limit. Therefore: LIMIT_EXCEEDED.

- Limits are not necessarily just about money. We can have velocity limits. Maximum 5 payments in 10 minutes.

Risk Engine - This behavior has characteristics that make us uncomfortable enough to apply additional controls
Risk assessment
      ↓
Policy decision
      ↓
Allow / Verify / Review / Reject
